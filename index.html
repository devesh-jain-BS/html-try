Cloud run coverage for App LCA

This branch adds automated coverage for cloud runs, the part of App LCA where a saved test runs in a suite on real devices and the build reports results. Tests are created from JSON goldens through the API. Each golden runs in its own suite on a free device the backend accepts, and its run is checked step by step from the result JSON.

The flow

01The gap and the broken tests

The Playwright suite covers live "Run all" runs in the editor. Cloud runs had no working coverage. Doing it through the UI means recording a test, saving it, building a suite, running it and reading the Builds page, which costs 10 to 15 minutes and two device allocations per feature. With about 30 features on two platforms that doesn't scale.

Two cloud-run API tests already existed, TC-686716 (Android) and TC-686717 (iOS). They had failed at suite creation since June with 422 One or more tests are not available in this project.

Cause: POST /api/v2/tests only creates an inactive shell. The PUT /api/v2/tests/:versionId is the real save that persists the steps and syncs TestHub, and a refactor had dropped it. The suite validator couldn't see the test.

Fix: createTestFromFixture now posts the shell, seeds any variables, globals or modules the test needs, then saves with the PUT. Both old tests go through it and get past suite creation. TC-686717 would still fail at its type step, because its hand-written fixture uses type where the runner expects type_text. Neither was re-run to green; the matrix supersedes them.

02The design

  • Goldens, not recordings. Each feature is a JSON fixture holding a complete saved-test payload plus an expect block. The Phase 0 action shapes (tap, type, validate, if/else, loops, AI) and the module and variable reference shapes were captured from saved regression tests. The Phase 1 shapes (gestures, sleep, extraction, app lifecycle, deeplink) were written from reads of the editor's serializer and the runner, then checked by saving and reading back, and by green builds.
  • One suite per golden, on a free device. The run first finds free devices the backend accepts, then gives each golden its own suite. This started as one suite per platform; that version queued every golden behind a single device when only one was free.
  • Per-step assertions. The run-detail API only links to the worker's result JSON. The suite follows that link and checks each step's status, error text and duration, plus loop iteration counts.
  • Apps: iOS uses the AWS DeviceFarm reference app and Android uses qa-playground.apk. Both are uploaded fresh every run, because regression apps expire on every deploy.

Three alternatives were rejected:

  • UI end-to-end per feature: too slow, and it asserts through a dashboard that is itself under test.
  • Driving the runner directly: it tests the engine, not the product.
  • Mocked build responses: no runtime coverage.

03How one run works

What happens when cloudRun.matrix.<platform>.test.js runs in the default per-test layout. The body is defineCloudRunMatrix in src/helpers/cloudRunMatrix.js; device planning is in src/helpers/cloudRunDevices.js. CLOUD_RUN_LAYOUT=per-app keeps the original single suite per app.

  1. Load goldens. Read every fixture for the platform and apply the name filters.loadFixtures
  2. Plan devices. Read the catalogue the backend accepts and the group's parallel count, ask a device source which devices are free, and make up to min(parallels, goldens) lanes spread across distinct models. The plan fails fast if it can't fit the time budget.planDevices · fetchCatalogue · fetchParallels · matchCatalogue · planAssignments
  3. Upload the app once per app, then look up its catalogue id.uploadCloudRunApp → uploadSampleApp · fetchAlcaCatalogId
  4. Create each test: POST the shell, seed the variables, globals or modules it needs, substitute their ids, then save with the PUT.createTestFromFixture · seedFixtureEntities · substituteEntityIds
  5. Re-plan right before triggering, since availability is a snapshot.planDevices
  6. Run the lanes. Each lane is a device. All lanes pull goldens from one queue; a free lane creates a suite for its next golden on its device and triggers it.runLanes · createSuiteForCloudRun · createSuiteRun
  7. Poll every live build about once a second overall, to stay under the 100-a-minute status limit. A 5xx or 429 falls back to the v2 build detail; a build whose status fails five times is aborted.readBuildStatus → getBuildStatus / getBuildStatusFromDetail
  8. Read each finished build as soon as it finishes, and follow its run's link to the result JSON.fetchBuildDetail · fetchRunDetail
  9. Assert each golden: it ran in its own build on its assigned device, then run status, failed-step count, per-step status, error text, duration bounds and loop iterations.assertRunAgainstExpectation · flattenSteps · loopIterations
  10. Clean up: abort unfinished builds, delete every suite created, then the tests, modules and globals.afterAll in cloudRunMatrix.js

Where free devices come from

  • Terminal service (TERMINAL_SERVICE_PASSWORD, staging): probes each candidate model and reports whether one is free. Its hold lasts 40 seconds and App Automate never reads it, so it steers the choice but can't reserve a device for a cloud run.
  • Admin App Automate feed (ADMIN_*, staging): the terminals App Automate allocates from, with real free counts. Wired, but not yet exercised live.
  • Pinned list (prod, or no credentials): CLOUD_RUN_<P>_DEVICES or the default, with availability unknown and capped by parallels.

Across the whole API suite, a redacting logger keeps credentials out of pactum's failure output. It is installed in setupEnv.js, globalSetup.js and globalTeardown.js.

Suite-level spec (iOS)

  • An unknown ios_app_id at trigger returns 400 with an app-not-found message.
  • An android_app_id on an iOS-only suite returns 400.
  • A bogus network_tracking value returns 400.
  • An ios_app_id override is applied: it shows in the trigger response, the build and the run, and a carrier test that only passes on that app passes.
  • Abort stops the build, and the pending test in an ordered block never gets a session.

How to run

Setup: run npm install in ALCA/api and decrypt the auth config for your environment. Never commit the decrypted file. The iOS app, AWSDeviceFarmiOSReferenceApp.ipa, is not tracked; the UI suite's download flow fetches it into its downloads folder.

iOS matrix on regression. module.existing needs that project's "Module Sync" module; elsewhere add CLOUD_RUN_EXCLUDE=module.existing.

cd ALCA/api
ENV=regression INCLUDE_MANUAL=true npx jest src/__tests__/cloudRun.matrix.ios.test.js

Suite-level and abort spec

cd ALCA/api
ENV=regression INCLUDE_MANUAL=true npx jest src/__tests__/cloudRun.suiteLevel.ios.test.js

Android matrix on prod. This uses real prod devices, so a person runs it.

cd ALCA/api
ENV=prod INCLUDE_MANUAL=true npx jest src/__tests__/cloudRun.matrix.android.test.js

cd ALCA/api
ENV=regression INCLUDE_MANUAL=true CLOUD_RUN_DEVICE_SOURCE=terminal-service CLOUD_RUN_ANDROID_DEVICES="Google Pixel 6:12.0,Samsung Galaxy S23:13.0" npx jest src/__tests__/cloudRun.matrix.android.test.js

Preview the device plan. Nothing is seeded or triggered.

cd ALCA/api
ENV=regression INCLUDE_MANUAL=true CLOUD_RUN_PLAN_ONLY=true npx jest src/__tests__/cloudRun.matrix.ios.test.js

Filters

  • CLOUD_RUN_FIXTURE=<substring> keeps only matching goldens. Prefer it to jest -t, which still seeds and builds everything.
  • CLOUD_RUN_EXCLUDE=a,b drops goldens whose names contain any entry.
  • CLOUD_RUN_IOS_DEVICES or CLOUD_RUN_ANDROID_DEVICES take "Name:version,…": the candidate list for discovery, or the pinned list.
  • CLOUD_RUN_DEVICE_SOURCE picks static, admin-feed or terminal-service; CLOUD_RUN_REQUIRE_AVAILABLE=true refuses the pinned list.
  • CLOUD_RUN_BUDGET_CAP_MIN (default 50) bounds a run; the plan fails fast when it can't fit.

    • The terminal service counts at most one free device per model.
    • A prod run of the per-test layout is pending.
    • The API suite needs the admin or terminal-service secrets in its own config; today they come from environment variables.
  • No Jenkins job yet. It needs an owner and a decision on prod or regression for Android signal.
  • Regression Android needs catalogue models made public on the staging pool.
  • Backend bugs to raise:
    • The status route returns 500 for builds with session-less runs.
    • Module create with blockId-carrying steps returns a missing id.
    • A device-queue timeout is reported as "invalid app URL".
    • Queued sessions keep asking for devices after an abort.
  • Runner: UI_STABILITY_WAIT_MS is undefined, so page checks read the screen once after a one-second pause. Checks right after a cold launch could flake.
  • Old tests: TC-686716 and TC-686717 remain. TC-686717's fixture still uses type, so it would fail at that step. Retire both once the matrix replaces them.
