Cloud-run automation: flow and file structure

2026-10-14 · Devesh Jain · for browserstack/BStackAutomation#87288

A cloud-run test is created once as code (a design compiled to a fixture) and run as often as needed by one Jest matrix that seeds it through the product APIs, runs it on a real device and asserts every step. This page shows both flows, the entry points, what goes in and out of every stage, which file does what, and a simpler folder structure that merges the parts.

1. The two flows at a glance

Create happens on a laptop, with no device: it ends in a fixture, the saved-test JSON the API takes plus the expected result of every step. Run happens per environment: the matrix takes each fixture through upload, seeding, suite, build and assertion.

2. Ways a test gets created

FlowWhenStepsStatus
Phase 1: a saved test existsThe test was recorded in the editor (email, biometric)capture <testId> dumps its steps and action shapes → write the design with the builders, mirroring the recording step for step → add the expected result → composeDone for email and biometric
Phase 2: only a DSL listSomeone hands over the steps as text, no recordingWrite the design straight from the DSL lines; a command the catalogue does not have yet needs one builder, captured once from any saved test that uses it → composeDone for the all-commands tests; a DSL-text-to-design parser would automate it later

In both flows the design is the source of truth. A design is one file: a list of named step groups (the word I used for them before was "section"), each with its steps, the entities those steps need, and the result every step must report.

3. Entry points

cd ALCA/api
node scripts/compose-cloud-run.js ios --design=email          # design → fixture JSON (+ the DSL coverage report)
node scripts/capture-golden.js <testHashedId> out.json         # saved test → step dump (phase 1 helper)
ENV=prod INCLUDE_MANUAL=true CLOUD_RUN_FIXTURE=email CLOUD_RUN_IOS_DEVICES="iPhone 16:18.0" \
  npx jest --config=jest.config.js src/__tests__/cloudRun.matrix.ios.test.js      # run one fixture

The matrix specs are tagged manual: they allocate real builds, so CI only loads them.

6. A simpler structure: the POM analogy

In the BDD framework the tree explains itself: a feature file says *what*, step definitions say *how each step runs*, a page object knows *the screen*. The cloud-run code has the same three roles, but today they are spread over helpers/cloudRunCatalogue, helpers/cloudRunDesigns, two helper files, four utils and three scripts.

BDD frameworkCloud runProposed home
Feature file: the scenario in business wordsTest design: the DSL steps and the expected resultcloudRun/tests/
Step definition: how a step executesDSL builder: how a command is written as the editor saves itcloudRun/dsl/commands.js
Page object: locators and screen actionsApp descriptor: screens, labels, unlock, proof textscloudRun/apps/<app>.js
Test data, hooksEntities to seed, run optionscloudRun/dsl/entities.js, cloudRun/dsl/runOptions.js
The runnerCompose (design → fixture) and the matrix (seed, run, assert)cloudRun/compose.js, cloudRun/run/

Proposed tree, one folder, every role visible:

api/src/cloudRun/
  dsl/
    commands.js      ← cloudRunCatalogue/dsl.js + expect.js (the result words belong with the commands)
    entities.js      ← cloudRunCatalogue/entities.js
    runOptions.js    ← cloudRunCatalogue/runConfig.js
  apps/
    mockeats-android.js, pulse-ios.js, shophard-ios.js, regression-ios.js   ← apps.js split, one page per app
  tests/
    allCommands.android.js  ← fullFlow.js
    allCommands.ios.js      ← fullFlowIos.js
    email.ios.js, biometric.ios.js
    entityKinds.js          ← cloudRunDesigns/entities.js (renamed; allInOne.js dropped)
  compose.js         ← cloudRunCatalogue/compose.js, with the coverage check inside
  run/
    matrix.js        ← helpers/cloudRunMatrix.js
    devices.js       ← helpers/cloudRunDevices.js
    seed.js          ← the createTestFromFixture part of utils/tests.util.js
    results.js       ← utils/cloudRun.util.js
  fixtures/          ← metadata/cloud-run/*.json (generated; or composed at test start and not committed)
  README.md
api/scripts/cloud-run.js   ← compose-cloud-run.js + capture-golden.js + dsl-coverage.js as one CLI: compose | capture | coverage

What this merges or removes: expect.js and index.js disappear into commands.js and compose.js; the three scripts become one CLI; allInOne.js and the POC day log leave the PR; the cloud-run seeding leaves tests.util.js, which goes back to the generic test CRUD the rest of the suite uses. The API wrappers (builds.util.js, testSuites.util.js, uploadApp.util.js) stay in utils with their siblings. File count stays about the same, but each file sits under the role it plays and nothing is named "catalogue", "design" or "golden" any more.

7. Decisions open

  • Commit the fixtures or compose at test start? Committed fixtures are reviewable and diffable, but they are 14k generated lines (#87555). Composing at start removes that PR; the designs stay the source of truth.
  • The word for a step group. "section" confused readers; scenario is the candidate.
  • Keep the coverage check? It enforces the playbook rule mechanically; it can go if the rule is reviewed by eye instead.
