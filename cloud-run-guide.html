Cloud-run PR review guide (#87288)

2026-10-13 · Devesh Jain · for the review of browserstack/BStackAutomation#87288

What the PR is

#87288 adds a generated cloud-run test suite for App LCA. A catalogue holds one builder per DSL command, designs are written against it, a composer turns a design into a saved-test fixture (JSON), and a matrix seeds that fixture through the product APIs, runs it on a real device and asserts every step. Nothing is recorded in the editor.

It is a stack of three PRs:

How it works at a glance

The top row runs offline on a laptop and produces the fixture that #87555 holds. The bottom row is what the Jest matrix does with each fixture against the product: upload, seed, pick a device, run, read the result and compare it with the fixture's expectation.

Reading order

Six files give the whole picture; the rest are details.

  1. cloudRunCatalogue/README.md: the map, the command table with where each action object came from, the entity kinds, the designs.
  2. cloudRunCatalogue/dsl.js: what one step object looks like and how a builder makes it.
  3. cloudRunDesigns/fullFlow.js: how a design reads (sections, steps, expectation).
  4. cloudRunCatalogue/compose.js: how a design becomes a fixture.
  5. utils/tests.util.js, createTestFromFixture: how a fixture becomes a real test through the APIs.
  6. cloudRunMatrix.js: how a fixture is run and asserted.

Then cloudRunDevices.js (which device, when) and utils/cloudRun.util.js (how the result is read and compared).

Logic flow, step by step

  1. Compose (offline, node scripts/compose-cloud-run.js): a design's sections call catalogue builders; the composer numbers the steps and writes <name>.<platform>.json with metadata.steps (ids still as placeholders) and expect (the status every step must report). The coverage script checks no sheet row is used twice.
  2. Seed (createTestFromFixture): POST the test shell, create the entities in dependency order, replace every {{entity:…}} placeholder with the real hashed id, PUT the steps. The test now exists in the product exactly as if saved in the editor.
  3. Plan and upload: the device list is checked against the catalogue and becomes lanes; each app is uploaded once per app and toggle set.
  4. Device and suite: a lane takes a golden from the queue, gets its device right before the suite (prod: the listed device; elsewhere: the first listed device the terminal service grants), creates one suite for that test with the design's suite options, and triggers it.
  5. Poll: build status once per 10 s per build, under the rate limit; on a terminal status it reads the build detail, one row per run (a dataset gives one run per row).
  6. Assert: run detail plus the cached result JSON give each step's status, error and duration; Jest shows one run-level row and one row per design section, each compared with expect.
  7. Clean up (afterAll): abort unfinished builds, delete suites, unlink datasets, delete tests, modules, globals and seeded entities.

Good to know while reviewing

  • The fixtures are generated. Never hand-edited; node scripts/compose-cloud-run.js reproduces them (only the random step ids differ). Spot-check #87555 rather than reading 14k lines.
  • The specs are manual. They allocate real cloud builds, so they run only with INCLUDE_MANUAL=true; CI just loads the files.
  • Verified on prod on 2026-10-08 to 2026-10-13: Android 100 steps on two dataset rows, iOS 101 steps on two rows, email 10/10, biometric 8/8 (biometric also green on regression).
  • Expected failures are declared, not hidden: the Android denied deeplink and the iOS double-tap check carry an expected failed status in the fixture because of known runner bugs (filed).
  • Config lives in #87999. Regression cloud runs need the terminal-service password from it, or TERMINAL_SERVICE_PASSWORD in the env.
  • Two candidates to drop from the PR: cloudRunDesigns/allInOne.js (superseded) and plan-cloud-run-poc.md (a day log).
  • Full reference: the Confluence page; section 2 has a collapsible end-to-end walkthrough.
